# Подготовка и публикация

## До первой публикации на GitHub

- Проверить авторство собственного кода и принятую MIT-лицензию; сторонние лицензии сохраняются.
- Создать репозиторий и включить Private vulnerability reporting; указать его реальный URL в README, UPDATES и документах приложения. Сейчас URL намеренно отсутствует.
- Создать зашифрованную офлайн-копию ключей и проверить восстановление, не добавляя ключи в Git.
- Назначить сопровождающего и определить канал срочных security-обновлений.
- Закрыть обязательные пункты RELEASE_CHECKLIST.md. Не выдавать один телефон за полную матрицу.

## Перед каждым релизом

1. Проверить Mozilla security advisories и `node scripts/check-engine-updates.mjs`.
2. Обновить versionCode (монотонно), versionName и CHANGELOG; сохранить applicationId.
3. Выполнить команды сборки README, обновить notices и повторить сборку.
4. Запустить verification и ручные сценарии на тестовых аккаунтах.
5. Подписать локально и выполнить `node scripts/check-release.mjs APK`.
6. Проверить upgrade поверх прежнего APK без удаления данных; зафиксировать результат.
7. Создать source ZIP: `python3 scripts/package-source.py`.
8. В отдельной распакованной копии собрать unsigned APK и проверить его.
9. Создать SHA256SUMS для готового APK и source ZIP, положить notices и release notes рядом.
10. Просмотреть состав архива, убедиться в отсутствии ключей, локальных путей, профилей и логов.

Публикация отдельно разрешается владельцем: открыть GitHub prerelease с tag v0.9.0-beta.1.
Не загружать APK до готовности документов и исходников. GitHub Actions не публикует автоматически.
Подписывать файл после формирования SHA256SUMS нельзя: хеш изменится.
Хеш с того же источника не заменяет проверку сертификата и доверенного адреса выпуска.

## Статус beta

В описании указать проверенные устройства, ограничения функций и известные симптомы.
Не обещать сроки стабильной 1.0 до результатов тестирования.
Для 1.0.0-rc.1 нужны пройденная матрица, воспроизводимые сценарии и проверенная схема обновлений.
